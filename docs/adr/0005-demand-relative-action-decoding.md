# Action decoder expresses order quantity in lead-times-of-demand, not fraction-of-shelf-space

`src/rl/encoders.decode_action` currently maps the agent's order action to an absolute quantity via `qty = int(order_frac × (capacity − inventory − pending) / K_active)`. This is invariant in *capacity-units* — `order_frac=0.5` always means "fill half of my per-SKU shelf slice" — but is **not invariant in demand-units**. The same `order_frac` translates into a wildly different cover horizon depending on how big the store is relative to the per-SKU sales rate: at capacity ≈ 250 and ~5 sales/tick it lays in ~5 ticks of cover; at capacity = 10000 with the same ~5 sales/tick it lays in ~200 ticks of cover, far beyond the 180-tick episode horizon.

The observation encoder is already mostly scale-invariant (`inventory / per_sku_capacity`, `rolling_sales / per_sku_capacity`, `cash / initial_cash`, `price / MSRP`), so the agent emits roughly the same action distribution across scales. The action decoder is what breaks: it multiplies that same action by an *absolute* free-space figure that grows linearly with capacity. The empirical consequence (seed 0, LLM fashion world, checkpoint trained at capacity ≈ 250): the agent emits `order_frac ≈ 0.7` on tick 0 in both regimes, which becomes ~170 units at training scale and ~7050 units at flagship scale (`capacity=10_000`). The flagship-scale order costs ~$175k up front, takes longer than the episode to sell, and equity ends ~$200k below baseline — even though the same checkpoint beats baseline by ~5× equity in-distribution. The reward function is correct and the policy is correct for its trained operating point; the decoder is the layer that fails to transfer.

**Decision — Order quantity expressed as a multiple of expected lead-time demand.** Replace the current decode rule with `qty = clamp(int(order_frac × demand_horizon × recent_sales_rate), 0, per_sku_free_space)`, where `recent_sales_rate` is the 5-tick rolling mean sales already computed for the observation encoder and `demand_horizon` is a new scalar field on `RLConfig` (default ~10 ticks of cover). The agent now learns "stock H lead-times of expected demand per SKU" — a quantity expressed entirely in demand-units, with no dependence on absolute capacity. The free-space clamp preserves the shelf-capacity invariant so the action still respects the physical store size. Two derived quantities follow: (a) the action's effective range scales with the realised sales rate, so a low-demand SKU receives small orders and a high-demand SKU receives large orders for the same `order_frac` value; (b) startup ticks (no rolling history) fall back to a configured `cold_start_qty` so the first order isn't pinned at zero.

Considered alternatives:

(a) **Domain randomisation over scales.** Widen `RLConfig.capacity_dist` and `balance_dist` to span the full deployment range, and stop overriding the LLM-world authored capacity/balance in `src/rl/train.py:_load_world_from_file`. This solves the symptom by training the agent to recognise scale and adjust its action distribution accordingly — and is strictly easier to implement (no decoder change, no architectural commitment). The reason we prefer the decoder change anyway is that it removes the scale dimension from what the policy must learn at all: one training distribution covers every deployment scale, and the agent's capacity budget is spent on the substantive pricing/ordering decisions instead of inferring "how big is this store" from observation features. Domain randomisation remains a useful complementary signal; nothing in this ADR forbids combining the two.

(b) **Per-store action calibration constant baked into the template.** Multiply `order_frac` by a hard-coded `action_scale` field on `StoreTemplate`. Reduces to the chosen approach when `action_scale = demand_horizon × base_demand`, but loses the per-SKU and per-episode adaptation that flows through `recent_sales_rate` — a high-demand fashion SKU should get larger orders than a slow-mover at the same `order_frac`, which a single per-store scalar can't express.

(c) **Recurrent policy with explicit action history.** Add a GRU/LSTM over `(obs, last_action)` so the policy can track its own past order quantities and self-correct. Architecturally heavier than the decoder rewrite, and addresses the symptom (the policy emits scale-inappropriate orders) rather than the root cause (the decoder is scale-dependent). Worth revisiting once the decoder change is in.

(d) **Reward normalisation.** Doesn't help: the action-to-qty mapping is wrong before reward enters the picture. The agent still emits a scale-inappropriate action and the env still translates it to an over-sized order; normalising the resulting reward only changes the scale of the policy gradient, not the action itself.

**Migration.** Public surface stays the same: `observation_dim(K_active)`, `action_dim(K_active)`, and the action range `[-1, 1]` are unchanged, so `Actor` / `Critic` architectures need no edit. `RLConfig` gains `demand_horizon: int = 10` and `cold_start_qty: int = 0` fields. `decode_action` gains two arguments (`recent_sales_rate: dict[str, float]` and `demand_horizon: int`); the env populates `recent_sales_rate` from the `sales_history` deque it already maintains for the observation encoder. The existing checkpoint at `runs/fashion_run` will not transfer because the action-to-qty mapping changes; a retraining pass is required after the decoder lands. The regression test that proves the change worked is paired CRN evaluation at two scales — small (capacity Uniform(150, 400)) and flagship (capacity Constant(10_000)) — sharing one trained model: the retrained agent should beat `BaselinePolicy` on equity at *both* scales, which the current checkpoint cannot do simultaneously.
