# PRD: Setup files as the deterministic simulation input

Status: ready-for-agent

Reference decision: `docs/adr/0017-setup-files-as-deterministic-input.md`. Removed-feature
log: `TODO.md`. This PRD completes the store→graph migration ADR 0011 documented but never
finished, and transitions the branch fully to the multi-echelon model with no legacy code.

## Problem Statement

To run a simulation today I have to write a Python file (`scenarios/*.py`). That one file
does three unrelated jobs at once: it fetches or LLM-generates world data, synthesises a node
graph, and wires policy *objects* onto nodes. The consequences I feel:

- I can't create, edit, or delete a simulation's inputs by hand — I have to edit Python.
- There's no single human-readable artifact that *is* the experiment. The persisted
  `scenario.json` is lossy: policies survive only as a class-name string with no parameters,
  so it can't reconstruct a runnable run.
- The codebase is bloated with two parallel worlds: a legacy `Store` model
  (`StoreTemplate`/`StoreInstance`/`make_stores`/`stores_df`, `world.py`, `world_loader.py`)
  living alongside the multi-echelon graph model I actually want, plus demand add-on layers
  (product life-cycle, per-(node,product) freshness) that complicate the core without being
  load-bearing for a first working version.
- RL and tuning still speak in `StoreTemplate` terms, so the legacy concept can't die.

## Solution

Split the workflow into two stages with a **file boundary**:

1. **Prepare data** → produce a *simulation setup*: a directory of human-readable, editable
   files that fully and deterministically define a run. The setup can be hand-authored,
   scaffolded by a deterministic script, or generated by the LLM world generator — in any
   mix. The directory holds two files:
   - `catalog.csv` — one row per product. LLM-generatable; the primary file the generator writes.
   - `setup.yaml` — `market`, `disruption`, `nodes` (incl. inventory, capacity, prices, and
     `policy: {name, params}`), `edges`, and `run` (`n_steps`, `start_date`, `world_seed`).
     Human-owned.

2. **Run** → `uv run python main.py run <setup-dir>`. No Python scenario file. The simulator
   loads the setup, resolves each node's policy from a name→class registry (injecting
   node/edge facts), derives all seeds from a single `world_seed`, runs, and writes outputs —
   including a **verbatim copy of the input setup files** as the reproducibility snapshot.

Running the *same* setup files always produces the *same* output. An A/B comparison of two
policies on a bit-identical world is "copy the setup directory, change only the `policy`
block." The legacy `Store` model, the `World` artifact, and the life-cycle/freshness demand
layers are removed (life-cycle/freshness documented in `TODO.md` for possible later re-add).

## User Stories

1. As a modeller, I want to run a simulation by pointing the CLI at a directory of data files, so that I never have to write or edit Python to define an experiment.
2. As a modeller, I want the product catalog stored as `catalog.csv`, so that I can open, edit, and diff thousands of products in a spreadsheet or text editor.
3. As a modeller, I want all non-catalog configuration in a single `setup.yaml`, so that the market, disruptions, nodes, edges, and run parameters live in one place I can hand-edit with comments.
4. As a modeller, I want to define each node's starting inventory, capacity, region, and selling prices in `setup.yaml`, so that I control the world's structure directly.
5. As a modeller, I want to choose each node's policy by name and give it parameters in `setup.yaml` (e.g. `policy: {name: order_up_to, params: {cover_horizon_ticks: 14}}`), so that I can change behaviour without touching code.
6. As a modeller, I want node/edge facts (capacity, unit cost, list prices, supplier ids, lead times) written exactly once on the node or edge and injected into the policy automatically, so that editing a number in one place can never silently diverge from a duplicate in the policy block.
7. As a modeller, I want the policy `params` block to contain only genuine hyperparameters, so that the file stays small and the meaning of each value is unambiguous.
8. As a modeller, I want to define topology as a list of `edges` (`supplier`, `buyer`, `lead_time`), so that I can express arbitrary multi-echelon DAGs.
9. As a modeller, I want a single `world_seed` in `setup.yaml` with per-node init and policy seeds derived from `(world_seed, node_id)`, so that I manage one knob and still get fully reproducible runs.
10. As a modeller, I want running the identical setup directory twice to produce bit-identical output, so that I can trust results and regression-test the simulator.
11. As a researcher, I want to compare two policies on an identical world by copying a setup directory and changing only the `policy` block, so that I get a true Common-Random-Numbers paired comparison for free.
12. As a modeller, I want the run output to include a verbatim copy of the input `catalog.csv` and `setup.yaml`, so that any output folder is self-describing and re-runnable.
13. As a modeller authoring a small graph (e.g. 3 nodes), I want to write `nodes:`/`edges:` by hand, so that tiny demos need no tooling.
14. As a modeller with a large catalog, I want a deterministic scaffolder (`main.py scaffold ...`) that emits a starter `nodes:`/`edges:` block I can then edit, so that I don't have to hand-write hundreds of sinks and factories.
15. As a modeller, I want the scaffolder to emit the same YAML format I would write by hand, so that scaffolded and hand-written setups are indistinguishable and editable.
16. As a modeller, I want to generate a catalog and market from a domain prompt with the LLM generator, so that the generator writes `catalog.csv` plus the `market:` block of a setup directly.
17. As a modeller, I want the LLM generator to write *only* data (catalog + market), never policies or topology, so that the generated parts stay cleanly separated from my hand-authored experiment wiring.
18. As a modeller, I want a generated setup directory to act as its own cache, so that re-running the generator with the same name loads the existing files instead of calling the LLM again.
19. As an RL practitioner, I want to train a policy against a specific setup directory's catalog and market, so that I can learn against the exact worlds I generate or hand-author.
20. As an RL practitioner, I want per-episode capacity, opening balance, and active-SKU subset to be sampled from ranges in the training config, so that the learned policy generalises across world scales while the world *data* stays fixed.
21. As someone tuning a policy, I want Optuna trials to evaluate against a setup directory's catalog and market with per-trial scale randomisation from the tuning config, so that the tuner optimises against a real world I chose.
22. As a maintainer, I want the legacy `Store` model fully removed (`StoreTemplate`, `StoreInstance`, `make_stores`, `stores_df`, `Scenario.stores`, `Scenario.is_graph`, `Scenario.from_world`), so that there is exactly one world model: the typed-node graph.
23. As a maintainer, I want the `World` artifact and both `world_loader`s removed, so that the setup directory is the single source of world data.
24. As a maintainer, I want the product life-cycle and per-(node,product) freshness layers removed for the PoC and documented in `TODO.md`, so that demand is simply `dist × market.demand_multiplier` and the core stays readable.
25. As a maintainer, I want the CRN per-catalog-product `world_rng` draw loop preserved (relocated out of `ItemRegistry` into the runner's catalog iteration), so that RL/tuning paired evaluation stays deterministic after `ItemRegistry` is removed.
26. As a maintainer, I want a single `Runner`/`build_world` with the `GraphRunner`/`build_graph_world` aliases and dead policy classes (`Policy` alias, `HeuristicPolicy`, `_HeuristicPolicyOld`, `NoopPolicy`) deleted, so that there is no duplicated or dead entry point.
27. As a maintainer, I want `Market` kept intact except `stage_multipliers`, so that seasonality, regional state, trend, cross-product correlation, elasticity, promo, supply side, and disruption events all still work.
28. As a maintainer, I want the run output's node table written as `nodes.parquet` (replacing `stores.parquet`), so that no artifact carries the retired "store" name.
29. As a new user, I want the README to explain the two-stage workflow with copy-pasteable commands for running, scaffolding, and LLM-generating a setup, so that I can get started without reading the source.
30. As a new user, I want at least one committed example setup directory I can run immediately with no API key, so that I can see the simulator work end-to-end on the first try.
31. As a contributor, I want CONTEXT.md updated to describe the setup-files model and drop retired terms, so that the glossary matches the code.
32. As a modeller, I want a clear, actionable error when `setup.yaml` references an unknown policy name, a malformed edge, a cycle in the graph, or a missing required field, so that I can fix my setup quickly.
33. As a modeller, I want `related_products` correlations encoded in a single `catalog.csv` column, so that cross-product market correlation still works from a flat file.
34. As a modeller, I want the existing example scenarios re-expressed as setup directories, so that the repo's runnable examples demonstrate the new model rather than the deleted one.

## Implementation Decisions

**Setup directory format.**
- A setup is a directory containing `catalog.csv` and `setup.yaml`.
- `catalog.csv` columns: `product_id, name, category, base_price, unit_cost, seasonality, related_products, init_stock_share`. `related_products` is a string-encoded list of `pid:weight` pairs separated by `;` (empty = none). Prices are scalars (no `Distribution` in the catalog).
- `setup.yaml` top-level keys: `market`, `disruption`, `nodes`, `edges`, `run`.
  - `nodes[]`: `id`, `type` (`factory|intermediate|demand_sink`), `region`, plus type-specific fields — factory: `produces_product_id`, `unit_cost`, `capacity_per_tick`, `inventory`, `list_price`; intermediate: `carried_products`, `capacity`, `tags`, `inventory` (map), `list_prices` (map), `min_order_imposed` (map); demand_sink: `product_id`, `demand_dist`, `income_rate`, `cash`. Each node may carry `policy: {name, params}` (sinks/factories may use defaults).
  - `edges[]`: `supplier`, `buyer`, `lead_time` (optional `per_product_lead_time` map).
  - `run`: `n_steps`, `start_date`, `world_seed`.
  - `Distribution`-valued fields (e.g. a sink `demand_dist`) use a small tagged form, e.g. `{kind: normal, mean: 10, std: 2}`, matching the existing `Distribution` taxonomy (`constant|uniform|normal|choice|log_uniform`).

**Setup I/O module (deep module).**
- `load_setup(dir) -> Scenario`: reads both files, validates, builds typed `Node`/`EdgeSpec`/`Scenario`, derives seeds, and resolves policies. The only module that knows the on-disk format.
- `write_setup(scenario, dir)`: inverse — writes `catalog.csv` + `setup.yaml`. Used by the LLM generator and the snapshot copy. Round-trip must be lossless for all data (policies are reconstructable because `{name, params}` is serialised, unlike the old lossy path).
- Validation surfaces a single clear error for: unknown policy name, missing required node/edge field, malformed `Distribution` tag, duplicate node id, and graph errors (delegated to `build_graph`: cycles, unreachable nodes, same-level supplier links).

**Determinism contract.**
- `setup.yaml.run.world_seed` is the only seed in the file.
- The loader derives each node's `init_seed` as `derive(world_seed, node_id)` and each node's `policy_seed` as `derive(world_seed, node_id, "policy")`, reusing the existing `_derive_seed` hashing in `src/sim/episode_sampler.py`.
- `allocation_rng` continues to derive from `world_seed` (ADR 0016). Same files ⇒ bit-identical run.

**Policy registry + fact injection (deep module).**
- A `{name: class}` registry maps stable snake_case names (e.g. `order_up_to`, `reorder_point`, `periodic_order_up_to`, `periodic_reorder`, `single_supplier`, `static_factory`, `default_demand_sink`) to policy classes.
- `build_policy(name, params, *, node, edges, policy_seed) -> NodePolicy` resolves the class, injects node/edge-derived facts (capacity, `unit_cost`, `list_prices`, supplier ids, lead times) and the derived `policy_seed`, then splats the remaining `params` as constructor kwargs. Policy constructors are refactored so these facts arrive via injection rather than being re-declared as required kwargs; `params` then carries only true hyperparameters.

**Topology scaffolder (deep module).**
- `scaffold_topology(catalog, spec) -> {nodes, edges}` is the deterministic successor to `world_to_graph`, decoupled from `StoreTemplate`. `spec` carries shop count, `sink_density`, region, and default node sizes. Output is YAML-serializable and identical in shape to hand-authored topology.
- Exposed via `main.py scaffold <catalog.csv> [options] --out <setup.yaml>`; it emits or merges a `nodes:`/`edges:` block.

**CLI (`main.py`).**
- `run <setup-dir> [--output DIR]` — load setup, run, export (default output `data/<setup-dir-name>/`).
- `scaffold ...` — emit starter topology.
- The old "pass a `scenarios/*.py` path" entry point is removed.

**Runner / scenario / demand.**
- `Scenario` becomes the in-memory loaded form: `catalog, market, disruption, nodes, edges, n_steps, start_date, world_seed`. Lossy `to_json/from_json`, `stores`, `is_graph`, `from_world`, store DataFrame views removed.
- `runner.py` keeps one `Runner`/`build_world`. The CRN per-catalog-product `world_rng` draw loop (ADR 0003) moves into the runner iterating `scenario.catalog` directly. `DemandSinkNode.demand_target` becomes `demand_dist.sample(rng) * market.demand_multiplier(pid, region, tick)` — no stage or freshness terms.
- `MarketParams` drops `stage_multipliers`; everything else stays.

**Removals (no legacy code).**
- Delete: `src/sim/world.py`, `src/sim/world_loader.py`, `src/tuning/world_loader.py`, `src/sim/freshness_curve.py`, `src/sim/lifecycle_clock.py`; `StoreTemplate`, `StoreInstance`, `make_stores`, `stores_df`; dead policy classes (`Policy` alias, `HeuristicPolicy`, `_HeuristicPolicyOld`, `NoopPolicy`); `ItemLifecycleParams`. `ItemRegistry` is removed (its CRN job relocates); if a thin catalog-iteration helper is convenient it may remain but must not own life-cycle.
- Out of scope: collapsing the textbook-policy two-hierarchy bridge.

**RL / tuning redesign.**
- Both load `catalog` + `market` from a setup directory (replacing `world_loader`'s cache/archetype/synthetic resolution). A small synthetic-setup helper may stand in when no setup dir is supplied.
- Both keep a programmatic per-episode/per-trial graph builder rewritten in `NodeInstance`/`EdgeSpec` terms (factory-per-active-SKU → trainable intermediate "S" → sink-per-active-SKU). No `StoreTemplate`.
- The old `StoreTemplate` randomisation fields (`capacity_dist`, `balance_dist`, `delivery_lag`, `holding_rate`, `order_fee`) move into `RLConfig` / tuning `Config` as randomisation ranges + node defaults.
- The RL `OrderUpToPolicy` CRN comparison anchor and paired-eval determinism are preserved.

**Output / DataExporter.**
- Snapshot = copy input `catalog.csv` + `setup.yaml` into `config/` of the output folder.
- Node static table written as `nodes.parquet` (replacing `stores.parquet`). Timeseries, run log, and overview PNG unchanged.

**Documentation.**
- Rewrite `README.md`: the two-stage workflow; the `catalog.csv` + `setup.yaml` anatomy; copy-pasteable commands for `run`, `scaffold`, and LLM-generate; the determinism + A/B-by-copy story; updated repo layout (no `World`, no stores).
- Commit at least one no-API-key example setup directory under `setups/` (e.g. a 3-node chain) plus a larger converted example; remove or convert `scenarios/*.py`.
- Update `CONTEXT.md` to the setup-files model; drop retired terms (`Store*`, `World`, life-cycle, freshness, `ItemRegistry`). Update `src/*/README.md` where they reference deleted concepts.

## Testing Decisions

Good tests here assert **external behavior** — given files, what object/run results — never
private internals. Prior art: `tests/sim/test_scenario_graph_roundtrip.py`,
`tests/sim/test_determinism.py`, `tests/sim/test_graph_dag.py`,
`tests/sim/test_node_construction.py`, and the tuning/RL determinism tests
(`tests/tuning/test_evaluator.py`, `tests/rl/test_eval_crn.py`).

Modules to test (all four selected):

- **Setup I/O** — `catalog.csv` + `setup.yaml` → `Scenario` → files round-trip is lossless;
  seed derivation from `(world_seed, node_id)` is correct and stable; **same setup dir run
  twice yields bit-identical run logs** (the headline determinism guarantee); malformed
  setups raise single clear errors (unknown policy name, missing field, bad `Distribution`
  tag, duplicate id, cyclic graph). Model after the existing scenario-roundtrip and
  determinism tests.
- **Policy registry + injection** — every registered name resolves to its class; `params`
  splat to the constructor; injected node/edge facts (capacity, list prices, supplier ids,
  lead times) reach the constructed policy and match the node/edge; unknown name raises.
- **Topology scaffolder** — given a catalog + spec, produces a valid DAG that `build_graph`
  accepts; sink-per-product / shop-count / `sink_density` expansion is correct; output is
  deterministic and re-loadable via `load_setup`.
- **RL/tuning episode builders** — per-episode/per-trial graph is built in node/edge terms
  from a setup dir; capacity/balance/active-subset come from config ranges; CRN paired-eval
  determinism is preserved (two identical specs ⇒ identical trajectories); the
  `OrderUpToPolicy` anchor still runs.

Tests for deleted code (freshness, life-cycle, `ItemRegistry`, stores, lossy JSON) are
removed, not adapted. A regression/snapshot test should cover at least one committed example
setup end-to-end.

## Out of Scope

- Collapsing the textbook-policy two-hierarchy bridge into a single hierarchy (flagged in ADR 0017).
- Re-adding product life-cycle and per-(node,product) freshness (tracked in `TODO.md` for a later PoC decision).
- Any new policy types or new market mechanics — Market stays intact minus `stage_multipliers`.
- A GUI or web editor for setups — files are edited in a text editor / spreadsheet.
- Schema-versioning/migration of setup files — single current format; no backward compat needed.
- Per-product life-cycle overrides (collapsed to global; deleted).

## Further Notes

- This branch (`multi-echelon`) goes all-in on the graph model; reverting is acceptable if the
  PoC disappoints, so no compatibility shims are kept.
- `pyyaml` is already available (transitive dep); `pandas`/`pyarrow` cover CSV. No new
  dependencies expected.
- Catalog sizes range up to ~3000 rows in existing worlds — CSV is the editability sweet spot.
- The `data/worlds/*/world.json` caches and `data/<run>/` outputs from the old model can be
  left in place or cleaned; they are not inputs to the new model.
